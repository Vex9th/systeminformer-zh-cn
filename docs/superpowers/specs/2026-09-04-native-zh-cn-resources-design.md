# 原生中文资源重构设计

状态：待评审

日期：2026-09-04

适用分支：`zh-cn`

## 1. 背景与结论

当前汉化通过运行时字典匹配、重写对话框模板、遍历子控件并替换文本。审计已确认这条路径存在内存越界、资源模板损坏、字体名截断、用户数据被误翻译以及全局 Hook 生命周期不安全等问题。现有“100% 覆盖率”只代表有限扫描范围内的字典命中率，不能代表真实界面覆盖、运行安全或视觉质量。

本次选择方案 B：将汉化迁移为 Windows 原生资源。每个资源宿主模块同时内嵌英文和简体中文资源，运行时按语言选择资源，不再修改已创建的窗口，不再根据英文原文查字典。

不采用独立 `.mui` 卫星文件作为当前阶段方案。项目包含主程序、多个插件和独立工具，卫星资源会引入逐模块、逐架构、逐语言目录及版本校验的部署复杂度，而仓库目前没有对应的加载和打包基础设施。嵌入式双语资源仍使用 Windows 标准资源语言机制，能先消除当前崩溃和误改数据的根因，并维持便携包结构。

参考：

- [Microsoft：MUI Resource Management](https://learn.microsoft.com/en-us/windows/win32/intl/mui-resource-management)
- [Microsoft：Development of MUI Applications](https://learn.microsoft.com/en-us/windows/win32/intl/development-of-mui-applications)
- [Microsoft：Creating a Resource-Only DLL](https://learn.microsoft.com/en-us/cpp/build/creating-a-resource-only-dll?view=msvc-170)

## 2. 目标

1. 消除运行时对话框模板重写、全局窗口 Hook 和按控件当前文本翻译。
2. 主程序、受支持插件及独立工具都能从自身模块加载 `zh-CN` 原生资源。
3. 中英文资源共享稳定的资源 ID；上游新增或修改资源时由机器检查明确失败。
4. 动态界面文本使用稳定 `IDS_*` 标识，不再以英文原文作为键。
5. 中文字体由资源模板完整声明，能在常用 DPI 下清晰显示且不裁切关键内容。
6. 发布结论只描述实际验证过的范围，不再用单一百分比代替质量证明。
7. README 缩短为用户真正需要的安装、差异、限制和验证说明。

## 3. 非目标

- 不改动 System Informer 的业务能力、驱动策略或权限模型。
- 不承诺一次迁移顺带修复所有上游历史缺陷。
- 不把 ARM64 的编译成功表述为 ARM64 真机运行通过。
- 不用机器翻译结果直接发布，也不建立自动翻译后自动打标签的流水线。
- 本阶段不引入 `.mui` 卫星文件；未来确有独立语言包需求时另行设计。

## 4. 总体架构

### 4.1 每个模块拥有自己的双语资源

资源按宿主模块放置：

- 主程序：保留现有英文 `.rc`，新增对应的 `zh-CN` 资源文件。
- 插件：每个插件在自己的 DLL 中内嵌同 ID 的简体中文资源。
- 独立工具：在自身 EXE 中内嵌简体中文资源。

中文资源声明：

```rc
LANGUAGE LANG_CHINESE, SUBLANG_CHINESE_SIMPLIFIED
```

英文资源继续由上游文件维护。中文文件复用同一组资源 ID，但不直接改写上游英文 `.rc`，从而减少同步冲突。不同 DLL 可以存在相同资源 ID，因为加载时始终带模块句柄；不能把所有插件资源塞入一个公共资源 DLL。

### 4.2 语言选择

保留现有用户可见的语言设置语义，但更换实现：

1. 程序启动早期读取语言设置。
2. `zh-CN` 映射为 `0x0804`，英文映射为 `0x0409`。
3. UI 资源加载助手先按目标 `LANGID` 查找，再回退到英文资源。
4. 插件通过自身 `DllBase` 加载资源，不能错误地从主程序模块取资源。
5. 找不到目标语言但英文资源存在时允许回退，并记录可诊断信息；两种资源都不存在时显式失败，不能伪造成功。

不全局改变通用的 `PhLoadResource` 语义。新增的语言感知助手只服务于 UI 资源，避免影响图标、二进制数据、版本信息等非本地化资源。

### 4.3 静态对话框与资源

- 为 `DIALOG`、`DIALOGEX`、菜单、加速键及其他用户可见资源提供同 ID 中文版本。
- 中文对话框直接写入中文标题和控件文本。
- 控件 ID、控件类型、顺序、样式及业务绑定必须与英文资源保持契约一致。
- 允许中文资源为了排版调整控件坐标和宽度，但不得改变业务含义、事件 ID 或可访问性关系。
- 不再解析或重写编译后的 `DLGTEMPLATE` / `DLGTEMPLATEEX` 字节。

### 4.4 动态文本

动态创建的菜单项、提示、状态栏、错误消息、搜索占位符等改用稳定资源 ID：

```cpp
PhLoadString(moduleBase, IDS_EXAMPLE_TEXT);
```

新增文本时先定义 `IDS_*`，再分别提供英文和中文 `STRINGTABLE`。技术标识、协议字段、文件路径或必须原样展示的第三方名称可以进入有理由的白名单，但不能靠宽泛目录或正则跳过检查。

迁移完成后删除“英文字符串 -> 中文字符串”的运行时字典和生成代码。迁移分支允许分批提交，但任何中间状态都不得发布。

## 5. 旧汉化层的处置

最终移除以下能力：

- `phtranslation` 的字典查找和生成表。
- 对话框模板二进制重写。
- `WM_INITDIALOG` 后遍历所有子控件并调用 `SetWindowText`。
- 进程级 CBT Hook 和相关全局状态。
- 运行时强制替换字体。
- 以旧字典命中数计算的“汉化覆盖率”。

删除旧文件前，必须先确认其中没有混入品牌名、无驱动构建或其他非汉化改动。混合文件采用逐段修改，不能直接用上游版本覆盖。

## 6. 字体与 DPI

中文对话框资源完整声明字体，例如：

```rc
FONT 9, "Microsoft YaHei UI", 400, 0, 134
```

实际字号和布局以视觉验收结果为准。字体名称必须由资源编译器完整写入，禁止手工传固定字节数。由于字体会影响对话框单位，中文资源允许独立调整布局。

最低验证矩阵：

- Windows 10、Windows 11。
- 100%、150%、200% 缩放。
- 浅色、深色主题。
- 中文、英文应用语言。
- 中文、英文系统环境。
- 插件启用与禁用的代表性组合。

自动检查只能证明资源结构和字体声明，不能证明视觉清晰。每个发布候选必须保留对应提交的截图或人工验收记录，并明确未覆盖的平台。

## 7. 校验工具与质量口径

删除旧百分比报告，建立三层验证。

### 7.1 源码资源契约

新增资源契约检查，至少验证：

- 英文与中文的对话框 ID 集合一致。
- 每个对话框的控件 ID、控件类型和关键样式一致。
- 菜单命令 ID、加速键命令 ID 一致。
- `STRINGTABLE` 中要求本地化的 ID 成对存在。
- 上游新增或删除资源时检查失败，并列出精确模块和资源 ID。
- 非文本资源不被中文文件意外覆盖。

契约文件记录模块、资源类型和允许差异的理由，不记录虚假的总覆盖率。

### 7.2 动态 UI 字面量守卫

扫描已知 UI 输出入口，包括窗口标题、对话框控件、菜单、列表、树、状态栏、通知、消息框、Task Dialog、搜索框和标签页。新增直接传入英文宽字符串的代码必须失败，除非命中带理由的精确白名单。

该守卫的目标是防止新增遗漏，不声称能从静态扫描证明所有运行路径已汉化。

### 7.3 构建产物验证

对实际生成的 EXE/DLL 逐模块检查：

- 预期模块集合完整。
- 简体中文资源语言 `0x0804` 存在。
- 英文回退资源存在。
- 对话框、菜单和字符串表结构符合契约。
- 每个架构的包只包含本次构建产物，不接受陈旧缓存覆盖源码产物。

## 8. 崩溃与数据安全回归

Windows 运行测试至少覆盖：

- 主窗口启动、刷新、正常退出。
- Options 对话框反复打开和关闭。
- 进程、服务、线程属性页。
- Run As 对话框及连续启动场景。
- 代表性插件页面。
- 对话框循环打开和销毁，收集崩溃转储与事件日志。
- 环境变量编辑器加载 `Path` 后，名称和值保持原样；取消时不写入，确认时只写入用户实际修改。
- 并发 Run As 使用唯一服务名，残留服务不会与新请求冲突。

x64 和 x86 必须实际运行。ARM64 只有在真实 ARM64 Windows 环境运行后才能标记为运行通过；否则只标记为构建通过。

## 9. CI、上游同步与发布

### 9.1 Pull Request 门禁

每个变更必须通过：

- 资源契约检查。
- 动态 UI 字面量守卫。
- 生成文件一致性检查。
- 各架构编译。
- PE 资源检查。
- 可执行架构上的 Windows 运行测试。

所有检查均为 fail-closed，不允许以 `|| true`、空结果或宽泛异常吞掉失败。

### 9.2 上游同步

同步任务只负责：

1. 合并或变基到明确的上游提交。
2. 运行资源差异检查。
3. 生成待人工处理的资源清单。
4. 创建可评审的分支或 PR。

同步任务不得自动机器翻译、自动推送正式分支、自动打版本标签或自动发布。

### 9.3 发布

发布只针对已评审的明确提交。发布页列出：

- 上游基线提交和汉化提交。
- 实际通过的架构、系统和 DPI。
- 未验证项。
- 无驱动构建的功能差异。
- 文件 SHA-256。

“编译成功”“结构检查通过”“运行通过”“视觉通过”分开陈述，不能合并成“100%”。

## 10. README 与维护文档

根 README 控制在约 50 行，只保留：

1. 项目是什么以及非官方性质。
2. 下载和最短使用步骤。
3. 与上游版的关键差异，尤其是无驱动构建。
4. 当前真实验证范围与已知限制。
5. 开发入口、许可证和上游链接。

维护细节拆分到：

- `docs/zh-cn/maintenance.md`
- `docs/zh-cn/verification.md`
- `docs/zh-cn/troubleshooting.md`

README 不再重复免责声明，不再用“界面完全一致”“文本全部中文”等无法由当前证据支持的绝对表述。

## 11. 迁移顺序

迁移在独立工作树和专用分支完成，按以下顺序提交：

1. 建立资源契约、字面量守卫及失败样例测试。
2. 增加语言感知的 UI 资源加载接口及单元测试。
3. 迁移主程序静态对话框。
4. 迁移各插件和独立工具静态资源。
5. 迁移动态菜单和动态 UI 字符串至 `STRINGTABLE`。
6. 移除旧 `phtranslation` 运行时层及其生成链。
7. 修复已确认的 Run As 唯一服务名问题，并补回归测试。
8. 重写 CI、同步和发布流程。
9. 精简 README，补齐维护、验证和排障文档。
10. 完成 Windows 运行和 DPI 视觉验收后才允许发布。

每一步都必须保持可审查。迁移期间不发布混合实现；旧层只有在资源迁移和回归测试齐备后才删除。

## 12. 验收标准

方案 B 完成需同时满足：

- 仓库不存在运行时模板重写、控件文本遍历翻译或全局翻译 Hook。
- 所有受支持资源宿主都包含英文和简体中文资源。
- 资源契约、字面量守卫、生成一致性、构建和 PE 检查全部通过。
- x64/x86 的关键运行场景通过，未出现新增崩溃或资源加载错误。
- `Path` 等用户数据不会因语言切换被改写。
- Run As 连续和并发执行不会复用固定服务名。
- 100%、150%、200% DPI 的代表性页面完成视觉验收，无已知字体名截断、明显模糊或关键文本裁切。
- README 不再宣称“100% 汉化”，发布说明准确区分验证层级。
- 同步和发布流程不存在失败后继续、自动翻译直发或陈旧缓存覆盖构建产物的路径。

## 13. 回滚策略

迁移按独立提交拆分。未达到发布标准时继续使用最后一个已知可用的正式版本，不发布中间构建。若新资源路径出现严重回归，回滚对应迁移提交，而不是重新启用已确认不安全的运行时模板重写和控件遍历翻译。

## 14. 已知风险与控制

- **工作量大**：按模块迁移并用资源契约持续收敛，但整个迁移期禁止发布混合实现。
- **中文布局与英文资源漂移**：上游同步后由资源 ID 和控件结构契约立即报错，人工处理布局差异。
- **动态字符串遗漏**：先建立 UI 输出入口守卫，再迁移调用点；运行验收补足静态扫描盲区。
- **插件资源错载**：测试必须从插件自身模块句柄加载，禁止默认落到主程序资源。
- **平台验证不足**：报告精确区分构建、结构、运行和视觉证据，不用百分比掩盖缺口。
